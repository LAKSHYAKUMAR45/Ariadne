# VS Code Extension Product Polish — Design

## Problem

The Ariadne VS Code extension now has the right primary surface: an Activity
Bar entry, a full React webview panel, task switching, task lifecycle controls,
checkpoints, editable todos/decisions/errors/questions, files, search, sync,
and Markdown export. The remaining product gap is not basic capability; it is
trust, handoff quality, and workflow speed.

Users still need clearer answers to:

- What has Ariadne captured for this task, and is passive capture working?
- What context would another agent receive if I resumed this task elsewhere?
- What should I do before I mark this task complete?
- How do I quickly start common task shapes without hand-entering the same
  todos/questions every time?
- How do I use Graphify and sync without falling back to chat commands or
  opaque output-channel text?

This design adds the next VS Code-only feature batch on top of the existing
webview architecture. It deliberately avoids larger platform work such as VS
Code Marketplace publishing, external plugin implementations, LLM/embedding
provider integrations, and team/cloud collaboration UI.

## Goals

- Make passive capture visible and trustworthy through an activity timeline
  and capture-health status.
- Make agent handoff first-class with a context preview/copy panel that uses
  the same ranked context builder as CLI/MCP/chat surfaces.
- Improve daily workflow with onboarding, task templates, completion review
  checks, and better Files/Search navigation.
- Add a Graphify tab that wraps the existing Graphify command surface from the
  extension host without moving CLI/filesystem work into the webview.
- Add a richer Sync tab that shows profile/setup/status information where the
  CLI can provide it, and makes command output easier to understand.
- Preserve the current architecture: local SQLite remains the source of truth;
  the React webview stays renderer-only; the extension host owns store, git,
  filesystem, clipboard/editor, CLI subprocess, and output-channel behavior.
- Ship as test-first, reviewable milestones with per-milestone commits, then
  build/package/install the final `.vsix` after whole-change review.

## Non-goals

- No marketplace publishing or Azure DevOps publisher setup.
- No real external plugins such as Jira, Linear, GitHub Issues, Slack, or
  Obsidian.
- No LLM-backed checkpoint summarizer, embedding provider, or hosted AI API
  integration.
- No team/cloud collaboration UI beyond better local wrappers for the existing
  CLI-backed sync commands.
- No replacement of the existing `@ariadne` chat participant or passive-capture
  listeners.
- No new daemon or backend process.

## Milestones

### Milestone 1 — Trust and handoff

Add surfaces that explain what Ariadne knows and what it will give to another
agent.

1. **Activity Timeline tab**
   - Reverse-chronological task activity across checkpoints, todos, decisions,
     errors, open questions, file captures, commits, and recent commands.
   - Filter chips for activity type.
   - Click-through to the owning tab/item for checkpoints, todos, decisions,
     errors, open questions, file captures, file search hits, and commit
     search hits. Recent command rows are display-only in this batch because
     there is no command-detail tab yet.
   - Uses a typed host DTO rather than making the webview infer activity from
     unrelated state arrays.

2. **Capture Health panel/card**
   - Shows current task target, workspace root, passive-capture setting,
     shell-integration availability, git extension availability, branch match
     status, last file capture, last command, last commit, unresolved diagnostic
     errors, and any recent passive-capture warnings the host can expose.
   - The first version can report capability and last-known state from existing
     store/context data; it should not require a persistent telemetry subsystem.

3. **Context Handoff panel**
   - Token budget selector with preview generated by `buildContext`.
   - Copy context to clipboard.
   - Open context as a Markdown/virtual document.
   - Show included sections and truncation notes so users understand what was
     omitted.

### Milestone 2 — Workflow polish

Add features that speed up common task starts and make completion safer.

1. **First-run onboarding**
   - A lightweight empty-state/welcome card inside the panel when no task is
     current or no task exists in the workspace.
   - Offers "Create task", "Import/sync tasks", "Open context help", and
     passive-capture explanation.
   - Does not auto-create or auto-switch tasks.

2. **Task templates**
   - Built-in templates: feature, bug fix, review, research, incident.
   - Template selection is optional during task creation.
   - Templates seed todos/questions/decisions only after the task is created,
     using existing `TaskStore` methods.
   - No persisted template customization in this batch. Built-in templates are
     hard-coded in the extension/webview contract so the first implementation
     has no settings, migration, or import/export surface.

3. **Review mode**
   - A pre-completion checklist for the current task:
     pending/blocking todos, unresolved errors, open questions, missing recent
     checkpoint and branch mismatch. Sync/export checks are included only when
     the host has explicit evidence from actions run in the current panel
     session; the review UI must label them as "unknown" otherwise.
   - Offers direct actions such as create checkpoint, resolve/open item, export
     Markdown, sync push, or mark done when checks are acceptable.
   - Does not prevent marking a task done; it informs and makes risks explicit.

4. **Files/Search polish**
   - File capture filters and better empty/error states.
   - "Open file" for captured paths when the file still exists in the
     workspace.
   - Search-result navigation improvements for file and commit hits.
   - Preserve the existing search-results stability fix.

### Milestone 3 — Advanced VS Code surfaces

Expose already-existing command surfaces visually.

1. **Graphify tab**
   - Buttons/forms for common subcommands: update current workspace, query,
     path, and explain.
   - Runs through extension-host code that reuses the existing Graphify helper
     pattern from `commands.ts`.
   - Shows install/setup guidance when Graphify is unavailable.
   - Streams or displays bounded output in the panel and logs full output to
     the Ariadne output channel.
   - Never lets the webview execute shell commands directly.

2. **Sync status/profile UI**
   - Show current sync profile and configured profiles when CLI support is
     available.
   - Show login/setup guidance when sync commands fail with auth/config
     errors.
   - Parse common command outcomes into structured status cards while retaining
     raw output access.
   - Keep push/pull/list-remote behavior compatible with the existing
     `syncCommands.ts` wrappers.

## Architecture

### Extension host

The host remains the only component that touches privileged APIs:

- `TaskStore` and cross-workspace registry access.
- Context building and Markdown export.
- File opening, virtual documents, clipboard, and VS Code commands.
- CLI subprocess wrappers for sync and Graphify.
- Passive-capture capability checks and output-channel logging.

The existing `src/webview/handleWebviewMessage.ts` dispatcher remains the main
testable boundary. It should gain request types for:

- `activity.list`
- `capture.health`
- `context.preview`
- `context.copy`
- `context.open`
- `task.createFromTemplate`
- `review.get`
- `graphify.run`
- `sync.profileList`
- Optional sync status/detail requests only for CLI commands that already
  expose stable machine-readable or simple line-oriented output. If a field
  would require guessing from arbitrary human text, omit that field and show
  the raw command output instead.

Complex response shapes should be defined in `src/webview/messages.ts` and
covered by dispatcher tests before UI work.

### React webview

The React app remains a renderer and request client:

- Add tabs/panels for Activity, Context, Graphify, and Review where they fit
  best in the existing tab rail.
- Keep Overview focused on current task summary and lifecycle editing.
- Keep Sync as the home for profile/status/actions.
- Reuse existing `bridge.request` patterns and inline banners.
- Keep state reconciliation explicit so cross-workspace task switching does
  not regress.

The webview must not infer security-sensitive or filesystem state from stale
props. When an operation depends on current workspace/task, ask the host.

### Data flow

1. Webview requests a typed operation.
2. Host validates payloads, resolves current task/workspace, performs the
   operation, and returns either typed data or a user-facing error.
3. Mutations return a fresh `WebviewState` when they affect task state.
4. Non-mutating panels can cache their own latest successful results but must
   reset when the selected task/workspace changes.

### Error handling

- All dispatcher validation failures return `{ ok: false, error }`.
- CLI-backed Graphify/sync failures include a concise panel message and log the
  fuller output to the Ariadne output channel.
- Unsupported capabilities, such as missing shell integration or missing
  Graphify binary, should render explicit setup guidance rather than silently
  hiding controls.
- Review mode is advisory; it should not block task status changes with hidden
  policy.

## Testing plan

Each milestone follows the same RED/GREEN/REVIEW pattern:

1. Host dispatcher tests for new request/response behavior and invalid input.
2. React component tests for primary user flows, loading states, and error
   states.
3. Type-check the nested webview package.
4. Run host extension tests.
5. Build/package the extension after milestone integration.

Regression coverage must include:

- Search results remain visible after a search.
- Cross-workspace task switching keeps subsequent requests bound to the
  selected workspace.
- Failed navigation/sync/Graphify requests do not update the UI as successful.
- Context preview/copy uses the selected task, not a stale task.
- Template task creation is atomic enough that partial seeding failures are
  surfaced clearly.

## Review and rollout

- Commit each milestone separately.
- Run TypeScript/React review after the feature batch is implemented.
- Build and package the `.vsix`.
- Install the final reviewed `.vsix` into VS Code Server, replacing the current
  manual install.
- Keep backup extension directories outside the VS Code extension scan path.

The optional SVG Activity Bar icon hardening already present in the worktree is
orthogonal. It can be kept as a small separate fix commit before or after this
batch, but it should not be mixed into feature commits.
